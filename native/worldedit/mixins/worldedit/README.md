# WorldEdit, native

The WorldEdit editor as a **native mod**: a [horizon-mixins](https://github.com/horizon-rust/horizon-mixins) bundle that becomes
part of the game binary instead of running as a sandboxed WebAssembly mod. It is the same command set as
`mods/official/worldedit` (the `.hmod`), but it runs inside the game that owns the world, so a fill writes
blocks through `Game::level_set` directly: no command, no packet, no block log, no command-length or
command-count limit.

## What the bundle does

`horizon-mixin.toml` declares six modules and nine hooks:

| Piece | What it is |
|---|---|
| `runtime.rs` | `mod worldedit` staged into `crates/horizon-client/src/game.rs`: the editor (selection, region maths, clipboard, shapes, undo). |
| `command.rs` | HEAD on `Game<'_>::run_command`: a `//command` typed on this machine. |
| `guest-command.rs` | HEAD on `Game<'_>::guest_command`: a `//command` from a guest of a hosted world, queued as typed so the server runs it with that player's state in place (`as_guest`). |
| `wand.rs` | HEAD on `Game<'_>::play_mouse`: the wand, taken before mining or item use starts. |
| `chat-suggestions.rs` | `mod worldedit_chat` staged into `crates/horizon-client/src/chat.rs`: the command table and the completion pass for the `//` prefix. |
| `chat-hook.rs` | HEAD on `ChatScreen::update_command_info`: completes `//commands` instead of parsing them as vanilla's unknown literal. |
| `schematic.rs` | `mod worldedit_schem` staged into `game.rs`: the three schematic formats, read and written. |
| `legacy_ids.rs` | `mod worldedit_legacy`: the 1.12 numeric block table `.schematic` files need, generated by `gen_legacy.py`. |
| `schem-menu.rs` | `mod worldedit_menu` staged into `game.rs`: the schematics menu, drawn over the pause menu's screen. |
| `schem-paths.rs` | `pub mod worldedit_paths` staged into `chat.rs`: the world's `schematics/` folder, its files, and the world the game opened, shared by the game and the completions. |
| `schem-input.rs` | HEAD on `handle_chat_input`: `//schem` in the chat screen opens the menu before the line reaches the server. |
| `schem-draw.rs` | HEAD on `draw_pause_menu`: the menu draws itself instead of the pause menu. |
| `schem-click.rs` | HEAD on `pause_click`: the menu's clicks. |
| `schem-key.rs` | HEAD on `key_pressed`: the menu's keys. |
| `open-world.rs` | HEAD on `open_world`: makes the world's `schematics/` folder and notes the world for the completions. |

The helpers are a few lines each: all the logic is in the modules, which are compiled inside the game
crate and therefore see the game's private fields and methods (no game to mod Cargo dependency).

## The wand

`//wand` puts a wooden axe named **WorldEdit Wand** in your inventory. With that axe held, **left click**
set position 1 and **right click** sets position 2, on the block you are looking at (`Game::pick`, so it
uses the game's own reach and outline raycast); the click does not mine, place or open anything. An
ordinary wooden axe is an ordinary axe, and the name is what marks the wand, so a renamed axe is a new
item to the editor. In single player on the server thread and on a LAN client, the click becomes the
command the player would have typed: a client sends it, the server's copy of the module runs it.

## Completions

The vanilla command tree does not know `//set`, so the chat screen used to answer `//` with "Unknown or
incomplete command" and completed nothing. The bundle takes over that prefix: names complete
(`//po` + Tab → `//pos1`), block arguments complete from the game's own block registry (`//set sto` + Tab →
`//set stone`), the direction arguments complete their six words, and the usage line is shown instead of a
parse error. Single-slash commands stay with the game.

A complete name that takes arguments completes with the space that starts them, so `//schem` + Tab gives
`//schem ` and its words, and Tab again picks one.

`//schem` completes too: its words (`list`, `load`, `save`, `delete`, `folder`) and then the world's own
schematics (`//schem load ` + Tab → `//schem load harbor`, again → `harbor-v2`; `//load ` the same). The
files are listed by the `worldedit_paths` module, which the game tells the world it opened, so a completion
points at the same folder the menu does.

## Browsing schematics

`//schem` with no argument opens a menu over the world: the `schematics/` folder of the world you are in,
every `.schem`, `.litematic` and `.schematic` in it, each with its format and size.

| Control | What it does |
|---|---|
| click a row, `↑` `↓`, `PgUp` `PgDn`, `Home` `End` | pick a file |
| **Load & Paste**, `Enter` | the file into the clipboard, then into the world where you stand (one `//undo` takes it back) |
| **Open Folder** | the folder in Explorer / Finder / the desktop's file manager, to drag files into |
| **Refresh**, `F5` | re-read the folder after adding or deleting files |
| **Done**, `Esc` | back to the world |

The folder is made when the world opens, so it is there before the first schematic, and `//schem folder`
opens it from the chat line too. The menu is the pause menu's screen: the world is not paused, the mouse
is free, and the pause menu is untouched when no menu is open. A guest of someone else's world has no
folder of its own, so `//schem` there stays what it always was: the host's list, in chat. On a server's
console, the menu becomes `//schem list` for the same reason (there is no window to draw in).

## Commands

```
//pos1 //pos2 [x y z]   (~ for where you stand; no arguments: your feet)
//sel [clear]           //wand, //we
//expand //contract <amount> [up|down|north|south|east|west]
//shift <amount> <dir>
//set <block>            //replace <from> [to]
//walls //outline //hollow //faces //overlay //center <block>
//sphere //hsphere <block> <radius>
//cyl //hcyl <block> <radius> [height]
//pyramid //hpyramid <block> <size>
//line <block> [thickness]
//copy //cut //paste //move <amount> <dir>
//count <block> //distr
//undo //redo //clearhistory
//schem                     (the menu)                //schem folder
//schem list                //schem load <name>       //load <name>
//schem save [name]         //schem delete <name>
```

Block names are `stone` or `minecraft:oak_stairs[facing=east]`; properties are optional and an exact state
is matched when you give them.

## Patterns

Every command that takes a block takes a **pattern**: a comma-separated list, picked at random for each
block of the region, so `//set stone,dirt` or `//cyl acacia_wood,minecraft:stone 4 3` mixes them.

```
//set stone,dirt                  the two, half and half
//set 70%stone,30%gravel          weighted
//replace stone,dirt air          the mask takes a list too (weights ignored)
//cyl acacia_wood,minecraft:stone 4 3
```

Commas inside `[...]` belong to the block's properties, not to the list:
`oak_stairs[facing=east,half=top]` is one block. Each edit bumps a salt, so the same pattern spreads
differently every time, and the pick is a hash of the position, so it never depends on the order the region
is walked in. A single block is placed for every position as before.

One operation may touch at most 250,000 blocks (`WorldEdit`'s default), the last 10 edits can be undone,
and an edit never loads a chunk: unloaded chunks are skipped. Editing needs build access and permission
level 2 (`//we` and `//wand` do not).

## Schematics

`.schem`, `.litematic` and `.schematic` files load into the clipboard, and `//paste` places them where you
stand.

```
//schem list                        what this world has
//schem load harbor                 a name in the world's schematics/ folder
//schem load harbor.litematic       the file name, extension and all
//schem load C:\builds\castle.schem  or a full path, spaces and all
//paste                             at your feet; //undo takes it back
//schem save castle                 the selection, as Sponge v2
//schem delete castle
```

Files live in `<world>/schematics/` (`//schem list` prints the path), and a name with a path in it is used
where it points, so a schematic does not have to be copied first. Formats:

| File | Format | What is read |
|---|---|---|
| `.schem` | Sponge v1, v2, v3 | the palette and varint `BlockData`, whichever of `BlockData`/`Blocks.Data` the version uses |
| `.litematic` | Litematica | every region, its palette and packed `BlockStates`; a region's negative `Size` is honored; regions are laid out relative to each other |
| `.schematic` | MCEdit, legacy WorldEdit | `Blocks`/`Data`/`AddBlocks` as 1.12 numeric ids, through the table in `legacy_ids.rs` |

The format is recognized by the file's contents, not its extension. A Sponge `Offset` (and a legacy
`WEOffset`) is subtracted, so the origin recorded when the schematic was made lands on you when you paste.
A palette entry this game has no block for is left out, and the load says how many.

Saving is Sponge v2 (`.schem`), which WorldEdit, FAWE, Axiom and Litematica all read.

Not yet: block entities and entities (chest contents, signs, armour stands) are not carried across — the
blocks are; a `//schem save` writes blocks only, and a file bigger than the 250,000-block edit limit is
refused rather than half-pasted.

## Build

The bundle is built by `horizon-mixins`, which stages a separate copy of Horizon and never edits the
checkout you are in:

```sh
git clone https://github.com/horizon-rust/horizon-mixins ../horizon-mixins
cargo fetch --locked --manifest-path ../horizon-mixins/Cargo.toml
# Validate the plan against this Horizon tree (writes nothing into it):
../horizon-mixins/target/debug/horizon-mixins plan \
  --workspace "$PWD" --mods "$PWD/mods/official/worldedit-native" --out ../we-plan.json
# Stage a patched copy and run the game crate's tests on it:
../horizon-mixins/target/debug/horizon-mixins check \
  --workspace "$PWD" --mods "$PWD/mods/official/worldedit-native" --out ../we-stage \
  --trust-native-mods
```

`check` runs `cargo test --locked --offline`, so the workspace's dependencies must already be cached
(`cargo fetch --locked`). The stage is published atomically and the original checkout keeps its bytes and
mtimes.

## Verified

Planned, staged, compiled (`cargo check -p horizon-client`) and run against this tree: in an offscreen single-player
game on its server thread, `//pos1 0 64 0`, `//pos2 2 66 2` and `//set stone` changed 27 blocks (confirmed with
vanilla `execute if block`), `//count stone` found them and `//undo` put them back; left click with the wand held
set position 1 to the block under the crosshair and did not mine it, while a plain wooden axe mined;
`//sphere glass 3` placed 123 blocks; `//set oak_stairs[facing=east]` wrote the state with that property.
Typed in the chat screen, `//po` + Tab became `//pos1`, `//set sto` + Tab became `//set stone` and
`//set stone,gl` + Tab completed only the second entry.

Patterns, over a 5x1x5 region: `//set stone,dirt` wrote 25 blocks as 13 stone and 12 dirt;
`//set 90%glass,10%gold_block` wrote 20 glass and 5 gold; `//replace glass,gold_block air` cleared all 25;
`//cyl acacia_wood,minecraft:stone 4 3` wrote 147 blocks as 76 acacia and 71 stone; and
`oak_stairs[facing=east,half=top]` stayed one block, its property comma intact.

Schematics, in an offscreen game on its server thread, each loaded, pasted, and the paste saved again with
`//schem save` and counted (`tools/verify_schem.py`):

| File | Loaded as | The saved box held |
|---|---|---|
| Sponge v2 `3x2x3` | `Sponge v2`, 18 blocks | 8 stone, 8 glass, 1 dirt, 1 `oak_stairs[facing=east,half=bottom,shape=straight,waterlogged=false]` |
| Sponge v3 `3x2x3` | `Sponge v3`, 18 blocks | the same 18 |
| Litematica `7x2x3`, two regions, one with `Size.x = -2` | `Litematica v6`, 26 blocks | 17 stone (the mirrored region's 8 included), 1 stairs, the rest air |
| MCEdit `2x2x2` | `MCEdit`, 8 blocks | 4 stone, 4 oak planks (1.12 ids 1 and 5) |

`//schem list` printed the folder and the four files, `//schem load <a Windows path>` read a file outside
the folder, and `//paste` placed each at the player's feet.

The menu, in the same kind of run: opening a world made `saves/<world>/schematics/` on its own; `//schem`
typed in the chat screen and submitted opened it (`screen: paused`, its four buttons among the screen's
widgets, and the screenshot in the run showed the list of four files with their formats and sizes);
**Load & Paste** on `harbor-v2.schem` reported "Loaded harbor-v2.schem (Sponge v2): 3x2x3, 18 blocks" and
"Pasted 18 blocks of harbor-v2.schem (Sponge v2)", and clicking another row first changed which file it
took; **Esc** closed it back to the world, the pause menu's own Escape and buttons still behaving. In chat,
`//sc` + Tab became `//schem`, and `//schem load ` + Tab became `//schem load harbor`, then `harbor-v2` on
the next Tab.

## Compatibility

Native hooks are raw function paths (`Game<'_>::run_command`, `Game<'_>::guest_command`,
`Game<'_>::play_mouse`), so a bundle is tied to the Horizon revision it was planned against. This bundle
was planned and compiled against the tree it sits in. For a launcher install, add the revision to
`horizon-mixin.toml`:

```toml
[compatibility]
horizon_revision = "<the Horizon commit the launcher builds>"
```

The `native_*` hook points in `crates/horizon-client/src/game/native_hooks.rs` are not compiled into this
tree (no `mod native_hooks;` declares them and there is no `native-hooks.json` catalogue), so this bundle
hooks the game's own functions instead of named hooks.

The chat input, the console and the guest command packet each drop a different number of leading slashes
before a command reaches `run_command`, so commands are matched by name (`//set` and `set` both work). A
name the vanilla dispatcher already has at its root is left alone; `move` belongs to `//clone`, not the
root, so `//move` is this mod's.

## Not in it

Brushes and tool bindings, `#clipboard`/`#existing`-style pattern sources, probability masks, `//deform`,
`//smooth`, `//naturalize`, `//stack`, `//regen`, biome tools, `//schem move`/`rename`, and block entities or
entities inside a schematic. The selection is not drawn in the world (there is no world-space line renderer
to hook yet): `//sel`, `//pos1` and `//pos2` report it in chat instead.
